02

The mental model: how Compose works

Think declaratively: UI is a description of the current state, not a sequence of view mutations.

Inputsstate + parameters
→
Compositionwhat UI exists?
→
Layoutwhere / how big?
→
Drawingwhat pixels?
Composition

Build the UI tree

Compose functions run and describe which UI nodes should exist for the current inputs.

Layout

Measure and place

Parents pass constraints down. Children report sizes; parents place them.

Drawing

Render content

Text, shapes, images and modifiers draw the visible result.

Composition vs recomposition

TermRecall it as
CompositionInitial execution that enters composables into the Composition and creates the UI description.
RecompositionRe-execution of affected composable scopes when observed state or inputs change.
SkippingCompose can skip eligible composables when inputs compare unchanged.
RememberingRetain a value in the Composition across recompositions at that call site.
Interview trap: Do not say “every state update redraws the whole screen.” State reads determine what is invalidated; Compose may recompose only affected scopes and may skip unchanged work. Composition, layout and drawing are distinct phases.

Why composables should be side-effect free

Recomposition can happen more often than expected, in a different order, or be discarded. A composable should describe UI from inputs. Do not directly make network calls, write databases, register listeners, or mutate external state from the composable body.

Good inside composition

Read state, calculate lightweight values, build UI, pass callbacks, create remembered objects.

Move out of composition

Network requests, analytics events, subscriptions, imperative SDK updates, file or database writes.

Snapshot state

mutableStateOf() creates observable Compose state. When a composable reads its value, Compose tracks that read. Writing a different value invalidates readers. Plain mutable variables and ordinary mutable collections are not automatically observable by Compose.

var count by remember { mutableIntStateOf(0) }

Button(onClick = { count++ }) {
    Text("Count: $count")
}

Use State<T> when exposing read-only state; use MutableState<T> where a caller is allowed to change it. Delegated syntax (by) is shorthand for reading / writing .value.

Other foundational concepts

CompositionLocal

Implicitly provides values down a Composition subtree, such as theme, density or layout direction. Use for cross-cutting tree-wide values, not as a replacement for explicit screen state or all parameters.

key()

Gives a composition group stable identity when the order or identity of repeated content changes. For lazy lists, prefer the list's key parameter.

remember

Retains a calculation result while the call site remains in the Composition. Keys invalidate and recalculate the remembered value.

Stateless composable

Receives current values and callbacks as parameters. It does not own the source of truth for those values.

remember vs rememberSaveable — tiny examples

remember

var expanded by remember {
    mutableStateOf(false)
}

Value is retained while the composable remains in the Composition.

rememberSaveable

var query by rememberSaveable {
    mutableStateOf("")
}

Suitable for small UI state that should be restored after Activity / system recreation.

State hoisting

Parent owns statesingle source of truth
→
Pass value downstate ↓
→
Child emits eventcallback ↑
→
Parent updatesnew state

Why? Reuse, testability, a single source of truth, coordination between siblings, and separation of UI rendering from state ownership. A component is commonly exposed as value + onValueChange or uiState + onEvent.

@Composable
fun NameField(value: String, onValueChange: (String) -> Unit) {
    TextField(value = value, onValueChange = onValueChange)
}

@Composable
fun ProfileForm() {
    var name by rememberSaveable { mutableStateOf("") }
    NameField(value = name, onValueChange = { name = it })
}
Memory phrase: State down, events up. Hoist state to the lowest common ancestor that needs to read or change it—not automatically to the top of the app.

State helpers: do not confuse these

APIWhat it doesUse when
remember(key)Cache a value until a key changes or the call site leaves Composition.Re-use an object / calculation across recompositions.
derivedStateOfCreates observable derived state; downstream updates only when the derived result changes.Inputs change more frequently than the UI needs to react (e.g. scroll index threshold).

Two quick distinctions: remember caches by keys; derivedStateOf derives observable state and can suppress downstream updates when the derived result is unchanged. An ordinary MutableList is not observable; use immutable replacement via state or a snapshot-aware collection.

Code patterns

LaunchedEffect: key controls restart
LaunchedEffect(userId) {
    // Cancelled and restarted when userId changes.
    viewModel.loadUser(userId)
}
rememberCoroutineScope: launch from event
val scope = rememberCoroutineScope()
val snackbarHostState = remember { SnackbarHostState() }

Button(onClick = {
    scope.launch { snackbarHostState.showSnackbar("Saved") }
}) { Text("Save") }
DisposableEffect: always clean up
DisposableEffect(lifecycleOwner) {
    val observer = LifecycleEventObserver { _, event ->
        if (event == Lifecycle.Event.ON_START) { /* ... */ }
    }
    lifecycleOwner.lifecycle.addObserver(observer)
    onDispose { lifecycleOwner.lifecycle.removeObserver(observer) }
}
Common trap: LaunchedEffect(Unit) means “once for this composition entry / stable key,” not “once for the entire process.” Do not put changing values in the key unless the effect should restart.
05

Layouts, Modifiers & lazy lists

Know which container to choose, how constraints work, and why modifier order matters.

Choose a layout

Row

Place children horizontally. Use horizontalArrangement, verticalAlignment, and scoped weight().

Column

Place children vertically. Use verticalArrangement, horizontalAlignment, and scoped weight().

Box

Stack / overlay children. Use contentAlignment or per-child align().

BoxWithConstraints

Read incoming max / min constraints and adapt child layout to available space.

Scaffold

App screen structure: top bar, bottom bar, FAB, snackbar host and content. Apply the provided innerPadding to content to avoid overlap.

Custom Layout

Use Layout when standard Row / Column / Box cannot express the measurement and placement algorithm. Measure children and place them.

Constraint mental model

Parentpasses min / max constraints ↓
→
Child measureschooses size within bounds
→
Parent placeschooses coordinates

A composable is measured under constraints from its parent. Modifiers can change constraints, measurement, placement, drawing, semantics and input.

Modifier chain order changes behavior

Clickable wraps padding

Modifier
    .clickable { onClick() }
    .padding(16.dp)

The clickable area includes the padded region because clickable is outside padding in the chain.

Padding wraps clickable

Modifier
    .padding(16.dp)
    .clickable { onClick() }

The outer padding is outside the clickable region; taps in that padding do not trigger the inner clickable.

API habit: Expose modifier: Modifier = Modifier on reusable composables and apply it to the root / first emitted UI element. Modifier is immutable; chaining returns a new chain.

Which list container?

ContainerUse whenRemember
Column / RowSmall, bounded set of children.All children are composed; use verticalScroll / horizontalScroll if needed.
LazyColumn / LazyRowLong or potentially large scrolling collections.Only visible / needed items are composed; use item / items.
LazyVerticalGridVertically scrolling grid.Use fixed or adaptive columns; item keys still matter.
LazyColumn {
    items(
        items = messages,
        key = { it.id },              // stable, unique, saveable ID
        contentType = { it.kind }     // useful for heterogeneous rows
    ) { message ->
        MessageRow(message)
    }
}

key

Identity: tells Compose which item is which across insertions, removals and moves. Prefer a stable unique ID, not the current list index.

contentType

Structure: groups similar item layouts so lazy layouts can reuse compositions more effectively in mixed-content lists. Most useful for heterogeneous lists.

Interview trap: Lazy does not mean “free.” Avoid expensive work in item content, use stable keys, avoid repeated list scans inside item lambdas, and profile scrolling in release builds.

Compose renders state. ViewModel coordinates state and events; repositories own data access.

UDF phrase: State flows down; events flow up. Prefer immutable UI state models and explicit actions such as onRetry(), onQueryChanged(query), or onItemSelected(id).

Flow vs StateFlow vs SharedFlow

TypeCold / hotCurrent value / replayBest mental model
Flow<T>Usually cold for standard builders; a Flow is an interface and can represent hot sources too.No built-in current value or replay contract.A stream description; collection runs the upstream work for cold flows.
StateFlow<T>Hot.Always has a current value; new collectors receive the latest value; conflates updates using equality.Observable state holder, usually for screen state.
SharedFlow<T>Hot.Configurable replay / buffer; no required initial value.Broadcast stream for multiple collectors; delivery depends on replay / buffer / active subscribers.
Subtle but important: A default MutableSharedFlow(replay = 0) does not retain an event for a collector that was absent. Treat important outcomes that must never be lost as state, or design explicit acknowledgement / delivery semantics.

ViewModel responsibilities

Good fit

Own screen UI state, respond to events, call repositories / use cases, coordinate coroutines, transform domain data into UI models.

Avoid

Holding Activity / View / composable references, storing huge UI trees, putting all data access in the UI, or using ViewModel as a permanent database.

Architecture memory: Route composable connects Android lifecycle + ViewModel. Screen composable is mostly stateless and preview-friendly. Repository abstracts data sources; use cases are useful when business logic deserves a separate reusable unit, not mandatory for every function.

Performance, stability & recomposition

Do not optimize by counting recompositions alone. Diagnose first, then measure.

Performance decision sequence

→
Diagnosetrace, profiler, layout inspector
→
Optimize the causestate reads / lists / stability / work
→
Benchmarkverify improvement

Stability: the useful interview explanation

ConceptMeaningPractical guidance
ImmutableValue cannot change after construction; properties are immutable and methods are referentially transparent.Prefer immutable UI models with val properties.
StableCompose can reliably know when the type's observable properties change.Use observable state correctly. Do not promise stability if the contract is false.
UnstableCompose cannot rely on equality alone to know whether its internal properties changed.Avoid in-place mutation that Compose cannot observe.
@Stable / @ImmutableAnnotations declare a contract to the Compose compiler.Do not add them as magic performance switches; only when the contract is true.
Modern Compose note: Strong skipping is enabled by default starting with Kotlin 2.0.20. With strong skipping, restartable composables are skippable even with unstable parameters; stable parameters are compared structurally, unstable parameters by instance identity. Confirm your Kotlin / Compose compiler version before describing project behavior.

Practical optimization reminders

State reads

Read fast-changing state as late as practical. A state read during composition can trigger recomposition; lambda-based layout / draw reads can sometimes defer work to a later phase.

derivedStateOf

Useful when inputs update more often than the UI needs. Example: show a “scroll to top” button only after index becomes greater than zero.

Lazy lists

Stable unique keys. Provide contentType for heterogeneous item layouts. Avoid indexOf() scans in each item. Use small Column / Row for small bounded collections.

Expensive calculations

Move data work out of composition; cache computations with remember(keys) only when appropriate. Do not use remember to hide incorrect state ownership.

Collections

Standard mutable lists are not observable Compose state. Publish a new immutable list through state or use snapshot-aware collections when mutating in place.

Measure, don't guess

Use profiling / tracing and benchmarks. Recomposition can be cheap; skipping has comparison overhead too. Optimize user-visible bottlenecks.

Defer state reads: the idea

// Read in composition (can recompose when the value changes)
val offset = listState.firstVisibleItemScrollOffset

// Defer the read to placement via a lambda modifier
Modifier.offset {
    IntOffset(x = 0, y = listState.firstVisibleItemScrollOffset)
}

This is a technique, not a blanket rule. Make sure the UI behavior is correct, then benchmark the actual screen.

Essential code patterns to memorize

Small code fragments that cover a large part of Compose interview questions.

1. Stateless child + hoisted state

@Composable
fun Counter(value: Int, onIncrement: () -> Unit) {
    Row(verticalAlignment = Alignment.CenterVertically) {
        Text("Count: $value")
        Button(onClick = onIncrement) { Text("Add") }
    }
}

@Composable
fun CounterRoute() {
    var count by rememberSaveable { mutableIntStateOf(0) }
    Counter(value = count, onIncrement = { count++ })
}

2. Lifecycle-aware state collection

@Composable
fun SearchRoute(viewModel: SearchViewModel) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    SearchScreen(
        uiState = uiState,
        onQueryChange = viewModel::onQueryChange,
        onRetry = viewModel::retry
    )
}

3. Private mutable state, public read-only StateFlow

class SearchViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(SearchUiState())
    val uiState: StateFlow<SearchUiState> = _uiState.asStateFlow()

    fun onQueryChange(query: String) {
        _uiState.update { it.copy(query = query) }
    }
}

4. Keyed effect vs event coroutine

Restart on key change

LaunchedEffect(articleId) {
    viewModel.load(articleId)
}

Start on click

val scope = rememberCoroutineScope()
Button(onClick = {
    scope.launch { snackbar.showSnackbar("Done") }
}) { Text("Save") }

5. Lazy list identity

LazyColumn {
    items(
        items = products,
        key = { it.id },
        contentType = { it.category }
    ) { product ->
        ProductRow(product)
    }
}

6. Modifier parameter pattern

@Composable
fun InfoCard(
    title: String,
    modifier: Modifier = Modifier
) {
    Card(modifier = modifier) {
        Text(title, modifier = Modifier.padding(16.dp))
    }
}
Code review checklist: Is state owned by the correct layer? Is the child reusable? Are effects keyed and cleaned up? Is Flow collection lifecycle-aware? Do lazy items have stable identity? Is the modifier respected?

Interview rapid recall

Read the question, answer in one sentence, then expand with a code example if asked.

State

Architecture

Runtime

What is recomposition?

Re-run affected composable scopes when observed inputs change; unchanged work may be skipped.

Effects

LaunchedEffect vs rememberCoroutineScope?

Effect-key / Composition-triggered coroutine vs event-triggered coroutine scope.

Effects

State holder with latest value vs configurable hot broadcast stream.

Collect a Flow in a lifecycle-aware way and expose it as Compose State.

Lists

Identity across changes vs grouping similar item layouts for reuse.

Horizontal vs vertical vs overlay / stacking.

Whether Compose can reliably know when a type's observable value changes.

Performance

Is recomposition bad?

No. It is normal; optimize only when profiling identifies a user-visible cost.

Common wrong answers to avoid

Do not saySay this instead
“remember survives rotation.”remember survives recomposition while its call site remains; rememberSaveable restores small saved UI state.
“ViewModel survives process death.”ViewModel survives configuration changes; restore small state with SavedStateHandle and persist durable data separately.
“LaunchedEffect runs only once.”It runs for a composition entry and restarts when its keys change.
“SharedFlow is always an event queue.”SharedFlow is a configurable broadcast stream; replay / buffer / subscribers determine delivery.
“Every list should use LazyColumn.”Use lazy layouts for larger or virtualized lists; regular Row / Column can be better for small bounded content.
“@Stable makes it faster.”It declares a contract. Use only when true and benchmark any performance benefit.

30-second verbal summary

“Compose is declarative: composables describe UI from state. State changes invalidate the scopes that read them and Compose may recompose or skip work. I hoist state to the lowest common owner, expose immutable UI state from a ViewModel, and collect StateFlow with collectAsStateWithLifecycle. I use remember for Composition-local retention, rememberSaveable for small restorable UI state, and effects only for work outside pure composition. For performance, I use stable lazy-list keys, keep state reads and work scoped appropriately, and profile before optimizing.”
